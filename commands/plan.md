$ARGUMENTS 요구사항을 분석하여 칸반 태스크로 분해한다.
**태스크 등록 전 반드시 사용자 승인을 받는다. 이것이 정상 흐름의 마지막 일괄 결재 지점이다**
(이후 실행 단계의 개입은 [human] 확인·모호함 질문·블로커 등 예외 상황에 한정된다).

## 사전 준비

1. `.claude/docs/kanban.md`에서 프로젝트 ID(project_id)와 에이전트 ID를 확인한다.
2. `get_board`로 현재 보드 상태를 확인한다 (중복 태스크 방지).
3. `.claude/docs/lessons.md`가 있으면 읽는다 — 과거 사이클에서 /retro가 승격한 교훈이다.
   인터뷰 질문과 태스크의 `참고:`/`스코프밖:` 작성에 반영한다 (같은 실수를 계획 단계에서 차단).

## Phase 1: 요구사항 인터뷰 (필수 — 생략 불가)

요구사항을 분석하고 관련 코드를 탐색한 뒤, **질문 없이 분해를 시작하지 마라.**
아래 항목을 확인한다:

- **범위**: 어디까지 포함하는가? 제외할 것은?
- **제약**: 기존 동작 유지 여부, 호환성, 성능 요건
- **검증 방법**: 완료를 무엇으로 확인하는가 (테스트 명령, 화면 확인, API 응답 등)
- **추론 필요 지점**: 코드 탐색 중 발견한 "추론으로 채워야 하는 부분"을 전부 나열하고
  "내가 이렇게 이해했는데 맞는가?"를 확인받는다

질문 규칙:
- **요구사항($ARGUMENTS)에 이미 명시된 항목은 재확인하지 않는다**
- 질문은 **한 번의 AskUserQuestion에 묶는다** (최대 4개)
- 4개 항목 전부가 이미 명시된 경우에만 인터뷰를 생략할 수 있다. 이때 "이해한 내용"을 요약 제시하고 넘어간다

모호한 부분을 추론해서 코드를 만드는 것을 막는 것이 이 Phase의 목적이다.

## Phase 2: 태스크 분해

분해 기준 — **태스크 = 순차 진행 중의 리뷰 체크포인트 (커밋 단위)**:
- 병렬 실행 단위가 아니다. 하나의 요청을 순차로 진행하면서 QA/리뷰를 끼워넣을 지점을 정하는 것이다
- 태스크 하나는 독립적으로 검증 가능하고 커밋 가능한 변경 단위여야 한다
- 의존 순서가 있으면 `선행:` 레이블에 고정 포맷으로 명시한다 (아래 참조)

각 태스크는 반드시 다음 형식을 따른다:

```
title: 한 줄로 작업을 이해할 수 있는 제목

description:
  첫 줄: 구체적인 작업 내용
  관련: 영향받는 파일, 모듈
  선행: #N (계획 문서의 태스크 번호. 의존이 없으면 생략. 이 포맷 외 자유 서술 금지)
  참고: 주의사항 (해당 시)
  스코프밖: 건드리면 안 되는 것 (해당 시 — 스코프 크리프 방지용)
  완료조건:
  - [auto] 에이전트가 스스로 검증 가능한 조건 (예: "uv run pytest tests/ -v 통과")
  - [human] 사람만 확인 가능한 조건 (예: "대시보드에서 카드 드래그 동작 확인")

priority: Critical / High / Medium / Low
assignee: 담당 에이전트
```

**완료조건 작성 규칙 (중요)**:
- Reviewer가 이 조건만 보고 Done/Rejected를 판정할 수 있어야 한다
- "잘 동작한다" 같은 모호한 표현 금지. 명령어, 파일, 응답값 등 확인 가능한 형태로 작성
- 모든 조건에 `[auto]` 또는 `[human]` 태그를 붙인다. 검증 주체가 불분명한 조건은 작성 금지
- 태스크당 1~4개

## Phase 3: 사용자 승인 (게이트)

분해 결과를 표로 정리하여 제시한다:

| # | 태스크 | 우선순위 | 담당 | 선행 | 완료조건 요약 |

AskUserQuestion으로 승인을 받는다. 수정 요청 시 반영 후 재승인.
**부분 승인** (일부 태스크만 승인) 시:
- 승인된 태스크만 Phase 4로 진행
- 승인된 태스크가 미승인 태스크에 의존(`선행:`)하면 해당 태스크는 Backlog로 등록
- 미승인 태스크는 수정 후 재승인받거나 폐기

**승인 전에는 절대 create_task를 호출하지 않는다.**

## Phase 4: 계획 문서 저장 + 보드 등록

승인 후에만 실행:

1. **계획 문서 저장**: `.claude/docs/plans/plan-YYYYMMDD-<주제>.md`에 인터뷰 결과를 저장한다.
   태스크는 "무엇을", 이 문서는 "왜와 경계"를 담당한다. 필수 내용:
   ```
   # 계획: <주제>
   ## 목표 (한 문장)
   ## 확정 범위 (포함 / 제외)
   ## 횡단 제약 (모든 태스크에 적용: 기존 동작 유지, 호환성 등)
   ## 전역 스코프밖 (건드리면 안 되는 것)
   ## 확인된 추론 (인터뷰에서 확정받은 이해)
   ## 태스크 번호표 (#N ↔ title ↔ task_id 매핑, 등록 후 갱신)
   ```
2. **플랜 레코드 생성**: `create_plan`(project_id, title=계획 주제, goal/scope_in/scope_out=인터뷰 결과)으로
   이 계획을 플랜으로 등록한다. 반환된 `plan_id`를 이후 태스크에 부여한다.
   플랜은 이 프로젝트를 하나의 의도 단위로 쪼갠 것이다.
3. 각 태스크를 `create_task`로 생성 (description에 완료조건·선행·스코프밖 포함,
   `참고:` 레이블에 계획 문서 경로 기입). `plan_id`와 `position`(분해 순서, 1부터)을 함께 전달한다.
4. `assign_task`로 담당자 할당
5. 상태 규칙 (기계적 적용, 재량 없음):
   - 선행 태스크가 없거나 모두 Done → `update_task_status` → Todo
   - 미완료 선행이 있는 태스크 → Backlog 유지
6. 계획 문서의 태스크 번호표에 실제 task_id를 기입
7. 최종 보드 현황 요약 + "실행은 새 세션에서 /plan-run 권장 (기획 대화의 잡음 차단)" 안내
