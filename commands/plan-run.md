플랜의 태스크를 순차 실행한다. 구현 → 자체 QA → 리뷰 → Done을 자율 순환하며,
사람 개입은 [human] 확인·블로커·반려 반복 시에만 요청한다.

이 커맨드는 소모품 세션의 진입점이다: /plan으로 기획한 뒤 /clear 하고 새 세션에서 실행하는 것을 전제로 한다.
의도(완료조건)와 상태(노트)는 전부 보드에 있으므로 이전 대화가 없어도 이어갈 수 있다.

## 튜닝 파라미터

드라이런 후 조정할 값들. 본문의 규칙은 전부 이 값을 참조한다.

- `N_DONE = 3` : 태스크 N개 Done마다 세션 지속 여부 확인 (한 번 "계속" 선택 시 다음 확인은 2개마다)
- `MAX_QA_LOOP = 3` : 한 태스크에서 자체 QA 실패→수정→재검증 반복 한도 (도달 시 강제 정지)
- `MAX_REVIEW_FAIL = 2` : 동일 태스크 Reviewer FAIL 한도 (도달 시 블로커)

조정 이력: 없음 (초기값). /retro 근거로 조정 시 여기에 기록 — 예: `N_DONE 3→2 (retro-20260715 근거)`

## 커밋 규칙 (자동 커밋 — 세 가지 전제 필수)

이 워크플로우에서 커밋은 부수 기능이 아니라 **리뷰 무결성의 전제조건**이다 (태스크별 diff 격리).
/plan-run 실행 자체가 이 규칙에 따른 커밋의 사전 승인이다. 단, 아래 전제를 벗어나는 커밋은 승인 범위 밖이다:

1. **브랜치 격리**: 자동 커밋은 작업 브랜치에서만. main/master에 직접 커밋 금지
2. **push 금지**: 자동 커밋 ≠ 자동 push. push·PR 생성은 사용자가 명시 요청할 때만
3. **범위 제한**: 이 태스크에서 변경한 파일만 개별 스테이징. `git add -A` / `git add .` 금지
   (무관한 로컬 변경이 섞이면 diff 격리가 훼손된다)

커밋 메시지는 `.claude/docs/COMMIT_CONEVENTION.md`를 따르고 태스크 ID를 포함한다.

## Phase 0: 복원

1. `.claude/docs/kanban.md`에서 프로젝트 ID(project_id)와 에이전트 ID를 확인한다.
   **브랜치 확인**: 현재 브랜치가 main/master면 계획 주제 기반 작업 브랜치 생성을
   사용자에게 제안하고, 승인 후 생성·전환한다. 작업 브랜치 없이 Phase 1 진입 금지.
2. **계획 문서 읽기**: `.claude/docs/plans/`에서 진행 중인 계획 문서를 읽는다.
   태스크의 `참고:` 레이블에 경로가 있으면 그것을, 없으면 최신 파일을 사용한다.
   여기에 횡단 제약·전역 스코프밖·확인된 추론이 있다 — 태스크는 "무엇을", 계획 문서는 "왜와 경계"다.
   **계획 문서 없이 구현을 시작하지 마라** (문서가 정말 없으면 사용자에게 확인).
3. **교훈 읽기**: `.claude/docs/lessons.md`가 있으면 읽는다 — 과거 사이클의 반복 방지 교훈.
   구현 중 해당 상황을 만나면 따른다.
4. `list_plans`로 활성 플랜을 확인하고, `get_plan`으로 그 플랜의 태스크를 position 순으로 조회한다.
   (플랜에 속하지 않은 미분류 태스크는 `get_board`로 함께 확인한다.)
5. **Review 상태 태스크가 있으면**: [human] 대기 항목을 사용자에게 제시하고 확인 여부를 묻는다
   (아래 "human 확인 처리" 규칙 적용). 확인 대기가 세션을 넘어 유실되지 않게 하는 장치다.
6. InProgress 태스크가 있으면 `get_task_detail`로 **최신 handoff 노트를 우선** 읽고 그 지점부터 재개한다.
7. 둘 다 없으면 Phase 1로.

## human 확인 처리 (공통 규칙)

[human] 조건의 확인을 사용자에게 요청할 때:
1. AskUserQuestion으로 확인할 항목을 구체적으로 제시한다
2. 사용자가 확인해주면 → `add_note`(note_type="review")로
   `human-verified: <항목> — 사용자 확인, <일시>`를 기록한 뒤 `update_task_status` → Done.
   **노트 없이 Done 전환 금지** — 판정 근거가 대화에만 남으면 세션과 함께 증발한다
3. 사용자가 "나중에"라고 하면 → Review 상태 유지, 대기 목록으로 보고

## Phase 1: 태스크 순차 루프

Todo가 소진될 때까지 반복한다. **동시에 하나의 태스크만 진행한다.**

1. **선택** (기계적 규칙, 재량 없음):
   - 타이틀이 `[retro]` 또는 `[lessons]`로 시작하는 태스크는 게시물이다 — 후보·Todo 승격 대상에서 항상 제외
   - Todo 중 `선행: #N`이 없거나 선행이 모두 Done인 태스크만 후보
   - 후보 중 우선순위(Critical > High > Medium > Low) 최상위 선택
   - 태스크 Done 처리 후: Backlog에 선행이 모두 Done이 된 태스크가 있으면 Todo로 승격
   - **후보가 없는데 Todo가 남아 있으면**:
     - **계측 (필수)**: 흐름을 막은 Review 정지 태스크에 `add_note`(progress,
       `"flow-blocked: [human] 대기 — 후속 태스크 진행 불가"`)를 먼저 기록한다 (/retro 측정 데이터)
     - 원인이 [human] 확인 대기(Review 정지 태스크) → 그 자리에서 "human 확인 처리"를 수행.
       확인되면 Done 처리 후 루프 계속, "나중에"면 원인 요약 후 정지
     - 원인이 블로커 → 원인 요약 후 정지
2. **착수**: `update_task_status` → InProgress + `add_note`(progress)로 구현 계획 기록
3. **구현**: 본 세션이 직접 구현한다
   - description의 완료조건과 `스코프밖:`을 계약으로 삼는다. 스코프 밖 변경 금지
   - **완료조건으로 해소되지 않는 모호함 발견 시 추론 금지. 사용자에게 질문한다**
   - **계획 문서의 전제와 충돌하는 사실 발견 시** (예: 계획이 가정한 API가 실제로 없음):
     `flag_blocker`로 기록 + 사용자 확인 후 재개. 조용히 우회하는 것 금지 —
     계획의 전제가 어디서 깨졌는지 기록이 남아야 한다
4. **자체 QA**: `[auto]` 완료조건의 검증 명령을 실제로 실행하고 출력(증거)을 수집한다.
   "될 것이다"는 검증이 아니다. 실행하지 못한 조건은 그대로 기록한다.
   `[human]` 조건은 검증을 시도하지 않고 "사람 확인 필요"로 기록한다.
   - **계측 (필수)**: 자체 QA 실패 시마다 `add_note`(progress, `"QA-FAIL n회차: <사유 한 줄>"`)를
     기록한다. 이 노트가 서킷브레이커 카운트의 근거이자 /retro의 측정 데이터다 —
     노트 없는 실패는 카운트할 수 없다
   - **서킷브레이커**: 자체 QA 실패→수정→재검증이 `MAX_QA_LOOP`회에 도달하면
     handoff 노트를 남기고 강제 정지 (컨텍스트가 디버깅 루프로 오염된 상태).
     카운트 대상은 자체 QA 실패 루프만이며, Reviewer FAIL은 별도 규칙(`MAX_REVIEW_FAIL`)이 담당한다
5. **handoff 노트**: `add_note`(note_type="handoff")로 아래 스키마를 반드시 채운다:
   ```
   완료한 것: ...
   검증 명령과 결과: 실행한 명령 + 실제 출력 요약
   검증 못한 것: 없으면 "없음"
   문제와 해결: <부딪힌 문제> → 원인: <진단> → 해결: <택한 방법과 사유> (없으면 "없음")
   버린 접근: 시도했다 폐기한 방법과 폐기 이유 (없으면 "없음")
   계획과 달라진 점: 계획 문서 대비 변경 (없으면 "없음")
   주의사항: 알려진 이슈, 엣지 케이스
   변경 파일: ...
   ```
   서사 필드(문제와 해결/버린 접근/계획과 달라진 점)는 "왜 이렇게 됐는가"의 기록이다 —
   유저 인사이트와 /retro 교훈 승격의 원료. QA-FAIL 노트와 중복 서술하지 말고 **해결 경위** 중심으로 쓴다.
   이 노트는 자체 QA 기록이자 세션 인계용이다. **Reviewer에게는 전달하지 않는다**
6. **커밋 + 리뷰 요청**:
   - 이 태스크에서 변경한 파일만 스테이징하여 커밋 (커밋 규칙 준수, 태스크 ID 포함)
   - `update_task_status` → Review
   - 커밋이 리뷰의 기준점이다: Reviewer의 diff는 "직전 태스크의 마지막 커밋 이후"가 되어
     항상 이 태스크의 변경만 담는다
7. **Reviewer 서브에이전트 실행**: Agent 툴(code-reviewer)로 신선한 컨텍스트의 리뷰어를 띄운다.
   프롬프트에 반드시 포함:
   - 태스크의 완료조건 전문과 `스코프밖:` 내용
   - diff 범위 지시: 이 태스크의 커밋(들)만 (`git diff <직전 태스크 마지막 커밋>..HEAD`)
   - **"[auto] 조건의 검증 명령을 직접 실행하고 그 출력으로 판정하라"** —
     diff 눈검사나 구현자의 주장이 아니라 재실행 결과가 판정 근거다
   - "완료조건 충족 여부를 조건별로 판정하라. 스코프 밖 변경이 있는지 확인하라.
     스타일 취향은 제외하라. 판정: PASS 또는 FAIL(사유)로 보고하라"
   - 구현 과정의 추론·handoff 노트는 전달하지 않는다 (결과물만 독립 평가하게 한다)
8. **판정 처리**:
   - Reviewer는 `[auto]` 조건만 판정한다. `[human]` 조건을 "아마 될 것"으로 통과시키는 것 금지
   - PASS + `[human]` 조건 없음 → `add_note`(note_type="review", Reviewer 에이전트 ID로 기록) → `update_task_status` → Done
   - PASS + `[human]` 조건 있음 → **Review 상태 유지**. 확인할 항목을 대기 목록에 기록하고
     다음 태스크로 진행 (확인 요청은 후보 소진 시점에 "human 확인 처리"로 — 매번 묻지 않는다)
   - FAIL → `update_task_status` → Rejected + 사유 노트 →
     **수정 시작 시 `update_task_status` → InProgress** → 4번부터 재수행.
     수정분은 **추가 커밋**(fixup 스타일)으로 쌓는다 — 원래 시도와 수정 시도가
     워킹 트리에 섞인 채 세션이 끊기는 것을 방지. Done 시점의 squash 정리는 선택
   - **동일 태스크 `MAX_REVIEW_FAIL`회 FAIL → `flag_blocker` + 사용자에게 보고 후 정지**
9. 다음 태스크로

## Phase 2: 세션 위생 (기계적 트리거)

"컨텍스트가 무거운 것 같다" 같은 자기평가는 신뢰하지 않는다. 아래 트리거만 따른다:

- **태스크 `N_DONE`개 Done마다**: 사용자에게 확인 질문. 중립적으로 묻지 말 것 —
  "N개 완료했습니다. handoff가 저장돼 있어 **지금 끊는 것을 권장합니다**. 계속할까요?"
  (기본값을 '끊기'로 기울인다). "계속" 선택 시에도 컨텍스트는 정리되지 않으므로
  다음 확인은 2개 Done마다로 당긴다.
  - **완주 예외**: 남은 Todo가 2개 이하면 묻지 않고 완주한다
  - **인터럽트 병합**: 이 확인과 [human] 대기 확인이 같은 시점에 발생하면 한 번의 질문으로 합친다
- **자체 QA 루프 `MAX_QA_LOOP`회** (Phase 1 4번): handoff 후 강제 정지
- **블로커 발생 시**: handoff 후 정지

정지 시 사용자에게 안내: "보드에 상태를 저장했습니다. /clear 후 /plan-run으로 이어가세요."

## 완료

Todo 소진 시:
1. `get_project_status`로 최종 요약을 보고한다:
   완료 태스크 / [human] 확인 대기 목록 / 반려 이력 / 블로커 / 후속 작업 제안
2. [human] 확인 대기 태스크가 있으면 마지막으로 "human 확인 처리"를 시도한다
3. **계획 문서 아카이브**: 계획의 모든 태스크가 Done이면 (Review 대기·블로커 없음)
   계획 문서를 `.claude/docs/plans/archive/`로 이동한다. 삭제하지 않는다 — 나중 참조용 기록이다.
   미완료 태스크가 남아 있으면 문서는 `plans/`에 그대로 둔다 (Phase 0의 "진행 중 계획" 탐색 대상)
